Claim 01 — atomicity

Both legs move, or neither does

Ravi sends 2,200 AED from Dubai; ₹30,000 is bound to his sister's college fees. The chaincode holds amounts as integers in minor units — 220,000 fils and 3,000,000 paise — so no floating-point value touches money at any point. Claim 03 — access control

Two ways to settle a transfer you shouldn't, both refused

These are the controls the design rests on, and neither can be demonstrated against a mock. Both were run against the live network.

One organisation acting alone

A Commit endorsed only by Org1MSP was submitted and ordered. The Validation Service rejected it, so the ledger never changed. 

OK: single-org commit did not take effect — state is still PREPARED

An organisation that is not a party

PlatformOrg (Org3MSP) is the NPCI platform node and regulator observer — a full channel member with Writer rights, so its proposals reach the chaincode rather than being stopped by a channel ACL. The contract's own party check is what turns them away.

The verification script fails loudly if a refusal comes from anywhere other than the contract's party check. A channel-level rejection would be a false pass, and would hide whether the chaincode's own access control works.

What this page does not show

The point of collecting evidence is to be clear about where it stops.

  • No throughput or latency figure. Nothing has been benchmarked, and it could not be measured honestly here — DRUNIX publishes amd64 images only, so every container ran emulated on Apple silicon.
  • One ledger, not two. Cross-chain proof verification is stubbed as a locally anchored hash. The atomicity argument holds for the state machine but has not been shown across two networks.
  • PlatformOrg runs no peer. It is a channel member with an identity and read access, which is what a regulator observer needs. Its own nodes are Phase 1.
  • No rupee or dollar saving is claimed. The figures above are a buffer ratio on synthetic data; converting one into money needs a balance-sheet size and a cost of capital this project does not have.
  • Token, pool, policy, attestation and payout contracts do not exist yet. Phase 0 implements settlement only. Balances come from a minimal in-contract map that the token contract replaces.
  • The endorsement policy is chaincode-wide. Fabric applies it to every function rather than only to Commit; narrowing it needs state-based endorsement.
